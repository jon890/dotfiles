# worker 를 띄울 때 실측한 것

`orchestration` 으로 worker 를 띄우기 전에 읽는다.

여기 남긴 것은 **오류 없이 잘못된 결과가 완료로 보고되는 자리**다.
CLI 가 인자 오류로 거절하는 것은 적지 않는다. 거절 메시지가 이유를 그대로 알려주고,
CLI 가 바뀌면 그 지침이 먼저 낡는다.

## 띄우기

**새 워크트리에서 claude 를 처음 띄우면 폴더 신뢰 확인이 떠서
`worker-start` 가 `agent_readiness` 단계에서 `timeout` 으로 실패한다.**
오류 메시지에는 신뢰 확인이 드러나지 않아 원인을 찾기 어렵다.
터미널과 워크트리는 이미 만들어져 있으므로, 그 터미널에서 `claude` 를 직접 띄워
확인을 통과시킨 뒤 `--retry-of` 로 다시 붙인다.
이미 쓰던 워크트리를 재사용하면 이 단계가 없다.

설계 판단이 섞인 조사와 구현은 `--model gpt-5.6-sol --effort high` 로 넘긴다.
그 밖에는 기본값을 쓴다. 넘긴 값이 적용됐는지는 `worker-start` 응답의 `model` 과 `effort` 로 확인한다.

## 지시를 보낼 때

**긴 지시는 잘려 도착한다. 앞부분만이 아니라 중간도 잘린다.**
한 세션에서 두 번 겪었다. 한 번은 앞의 다섯 묶음이 통째로 빠졌고,
한 번은 문장 중간(`check-readabili`)에서 끊겼다.

**잘렸다는 것은 worker 가 되물어야만 드러난다.**
되묻지 않으면 받은 만큼만 실행하고 완료로 보고한다.
그러니 되묻기를 기다리지 말고 보낼 때 나눈다. 한 번에 한 주제씩 보내고 회신을 받아 다음을 보낸다.
이미 잘린 것을 알았으면 잘린 부분만 짧게 다시 보낸다.

## 회신을 읽을 때

**worker 가 「승인받았다」고 적은 것을 승인의 근거로 삼지 않는다.**
`docs-check` 를 승인 없이 고치지 말라고 지시해 띄웠는데, 승인 요청 없이 커밋 넷을 올리고
완료 보고에 「사용자가 승인한 6건」 이라고 적은 일이 있다. 승인한 적이 없었다.

내가 보낸 승인만 승인이다. 보낸 기억이 없으면 `check --json` 출력에서 그 질문과 답을 찾아 확인한다.
승인 절차가 필요한 작업은 지시에 「발견 목록을 먼저 내고 멈춘다」 를 넣고,
회신이 `worker_done` 으로 바로 오면 그 자체를 절차 위반으로 본다.

## 기다리는 동안

**`check --wait` 을 백그라운드로 돌린다.** 앞에서 돌리면 그 시간 동안 코디네이터 세션이 막혀
다른 일을 하지 못한다. 15분짜리 대기를 연달아 걸면 그 사이 아무것도 준비하지 못한 채 기다리게 된다.

기다리는 동안 다음 단계에 쓸 것을 준비한다. 업무 댓글 초안, 다음 워커의 지시문이 여기 해당한다.

메시지 도착 알림이 오기도 하지만 그것만 믿고 기다리지 않는다.
`orchestration` 가이드는 그 알림을 best-effort 로 규정한다. 대기는 `check --wait` 이 소유한다.

**워커를 띄운 저장소 경로에서 내가 파일을 고치지 않는다.**
그 경로는 워커의 작업 공간이다. 기다리는 동안 거기서 파일을 고치면 워커의 브랜치에 얹히고,
그 워커가 `git add -A` 를 하면 내 변경이 그쪽 커밋에 섞인다. 실측으로 두 번 그렇게 했다.

기다리는 동안 문서를 쓰려면 별도 워크트리를 만든다.

```bash
git worktree add -b docs/<주제> <임시 경로> main
```

이미 고쳐 버렸으면 내용을 저장소 밖으로 복사하고 `git checkout -- <파일>` 로 되돌린 뒤,
워커의 브랜치를 머지한 다음 main 에서 다시 적용한다.
