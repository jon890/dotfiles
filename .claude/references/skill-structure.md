# 스킬 문서 구조

**목표: 스킬을 처음 여는 사람이 무엇을 하는 스킬인지, 어떤 순서로 도는지, 지금 어느 단계인지를 차례로 알게 한다.**

어느 층을 고칠지는 [`skill-sync.md`](skill-sync.md) 가, 문장을 유지할지 지울지는
`~/.claude/skills/harness-cleanup/references/judgment.md` 가 소유한다.
이 문서는 **남기기로 한 것을 어디에 어떤 순서로 두는지**만 소유한다.

## 문서 구성

`SKILL.md` 는 위에서 아래로 이 순서를 갖는다.

| 층 | 무엇을 담나 | 분량 |
| --- | --- | --- |
| 목표 | 이 스킬이 끝났을 때 무엇이 참이 되는지 한 문장 | 1줄 |
| 워크플로우 개요 | 단계 전체를 한 화면에서 보는 표 | 표 하나 |
| 워크플로우 상세 | 단계마다 하나씩. 그 단계에서만 필요한 것 | 단계당 한 절 |

읽는 사람이 세 층을 순서대로 만나야 한다.
개요를 건너뛰고 상세부터 나오면 전체 길이를 모른 채 첫 단계를 시작하게 된다.

## 1층. 목표

제목 바로 밑에 굵은 글씨 한 문장으로 둔다.

```markdown
**목표: 외부로 나갈 본문을 등록 전에 실제 렌더링으로 보여주고, 사용자가 읽은 뒤에 등록한다.**
```

- **완료 조건으로 쓴다.** 무엇을 다루는 스킬인지가 아니라 끝나면 무엇이 참인지를 적는다.
- 목표가 둘 이상 나오면 스킬을 나눌 때다. 완료 조건과 실행 리듬이 다른 것이 섞인 신호다.

목표 밑에는 원칙을 둘 수 있다. 판단이 갈릴 때 어느 쪽으로 기울지를 정하는 문장만 남긴다.

## 2층. 워크플로우 개요

단계 전체를 표 하나로 둔다.

| 열 | 담는 것 |
| --- | --- |
| 단계 | 번호. 실행 순서와 같아야 한다 |
| 이름 | 그 단계가 무엇을 하는지 |
| 통과 조건 | 다음 단계로 가도 되는지 판정하는 관측 가능한 사실 |
| reference | 그 단계에서 읽을 파일. 없으면 비운다 |

- **번호는 실행 순서다.** `4절이지만 실행은 1절 직후` 같은 경우에는 번호를 다시 매긴다.
- **통과 조건은 관측 가능한 사실로 적는다.** `확인했다` 가 아니라 `종료 코드가 0 이다`,
  `대상 파일 수가 1 이상이다` 처럼 무엇을 보고 판정하는지를 적는다.
- 분기가 있으면 표 뒤에 발동 조건만 한 줄로 적고 상세는 해당 단계나 reference 로 보낸다.

조건부로만 도는 전체 흐름이 따로 있으면(핫픽스, 되돌리기 같은 것) 별도 표로 나눈다.
한 표에 섞으면 매번 도는 단계와 어쩌다 도는 단계를 가려 읽어야 한다.

## 3층. 워크플로우 상세

단계마다 절 하나를 둔다. 제목은 개요 표의 번호와 이름을 그대로 쓴다.

한 절에는 다음을 담는다.

- 그 단계에서 할 일
- 붙여넣어 실행할 수 있는 명령
- 그 단계에서만 걸리는 함정과 실측 근거
- 판정이 갈리는 곳의 기준

다음은 담지 않는다.

- 다른 단계에서 쓰는 값과 절차
- 형제 스킬이 소유한 절차. 넘길 값과 부르는 시점만 남긴다
- 스크립트의 docstring 과 `--help` 가 이미 말하는 것
- 매 실행에 필요하지 않은 복구 절차. 발동 조건만 남기고 reference 로 내린다

### 명령은 붙여넣어 돌아가야 한다

**플레이스홀더를 `<이름>` 으로 쓰지 않는다.** 셸이 입력 리다이렉션으로 해석해 실행 전에 죽는다.

```bash
gh release create "$TAG" --title "$TAG" --notes-file "$NOTES"   # 이렇게
gh release create <태그> --title "<태그>" --notes-file <본문파일>  # 이러면 죽는다
```

값을 변수로 두고 블록 앞에서 무엇을 채우는지 한 줄로 적는다.
`~/.claude/skills/harness-cleanup/scripts/run_doc_snippets.py` 가 이것을 실제로 돌려 확인한다.

## references 로 내리는 기준

`SKILL.md` 가 길어지는 것 자체는 판단 근거가 아니다. 아래 조건에 해당할 때 내린다.

| 조건 | 예 |
| --- | --- |
| 특정 상황에서만 필요하다 | 충돌 복구, 되돌리기, 인증 실패 대응 |
| 한 단계 안에서만 쓰는 상세 절차다 | 등록 양식의 항목별 작성법 |
| 목록이 길고 자주 바뀐다 | 고정값 표, 판정 기준 목록 |

내릴 때 본문에는 **발동 조건과 읽을 경로**를 남긴다. 내용을 요약해 두지 않는다.
요약을 남기면 두 곳이 같은 것을 말하게 되고 한쪽만 고쳐진다.

참조는 그 단계 옆에 둔다. 문서 끝의 참고 자료 목록은 어느 단계에서 읽어야 하는지를 알려주지 않는다.

## 이 구조를 쓰지 않아도 되는 것

순서가 없는 스킬은 개요 표를 만들지 않는다.
명령 카탈로그나 조회 도구 설명이 여기 해당한다. 그런 문서는 목표 한 줄과 분류된 목록으로 족하다.

판정 기준만 담는 스킬도 마찬가지다. 단계가 아니라 축으로 나뉘므로 축마다 절을 둔다.

## 고친 뒤 확인하는 것

`harness-cleanup` 으로 감사한다. 그 스킬의 「스킬 구조와 유지보수성」 축이 이 문서를 기준으로 판정한다.

```bash
python3 ~/.claude/skills/harness-cleanup/scripts/collect_targets.py "$REPO" --scope "$SCOPE"
python3 ~/.claude/skills/harness-cleanup/scripts/run_doc_snippets.py "$SKILL_MD"
```

`$SCOPE` 는 저장소 루트 밑의 스킬 디렉터리다.
`run_doc_snippets.py` 는 블록을 그대로 실행하므로, 저장소를 바꾸는 명령이 든 문서는
저장소 밖에서 돌려 그 명령이 닿지 않게 한다.
